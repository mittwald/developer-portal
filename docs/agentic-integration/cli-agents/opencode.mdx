# opencode with mittwald AI Hosting

<PlanCompatibility features={["ai"]} />

[opencode](https://opencode.ai) is a command-line coding agent that supports
OpenAI-compatible providers through the `@ai-sdk/openai-compatible` adapter, so
mittwald AI Hosting needs no special handling.

## Installation {#installation}

opencode 2.x and 1.x are published as different npm packages:

```bash
# opencode 2.x
npm install -g @opencode/cli

# opencode 1.x
npm install -g opencode-ai
```

Both versions install the same `opencode` command, so they can't be installed side by side.
Remove a 1.x installation before you install 2.x.

Check the install:

```bash
opencode --version
```

## Pointing opencode at mittwald AI Hosting {#configuration}

opencode reads configuration from either location:

- **Global:** `~/.config/opencode/opencode.json`
- **Per project:** `opencode.json` in the project root

```json
{
  "$schema": "https://opencode.ai/config.json",
  "model": "mittwald/Qwen3.8-27B-NVFP4",
  "provider": {
    "mittwald": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "mittwald AI Hosting",
      "options": {
        "baseURL": "https://llm.aihosting.mittwald.de/v1",
        "apiKey": "sk-..."
      },
      "models": {
        "Qwen3.8-27B-NVFP4": {
          "name": "Qwen3.8-27B-NVFP4",
          "reasoning": true,
          "tool_call": true,
          "limit": { "context": 256000, "output": 32768 }
        },
        "Qwen3.6-35B-A3B-FP8": {
          "name": "Qwen3.6-35B-A3B-FP8",
          "reasoning": true,
          "tool_call": true,
          "limit": { "context": 256000, "output": 32768 }
        },
        "gpt-oss-120b": {
          "name": "gpt-oss-120b",
          "reasoning": true,
          "tool_call": true,
          "limit": { "context": 131072, "output": 32768 }
        },
        "GLM-OCR": {
          "name": "GLM-OCR",
          "tool_call": false,
          "limit": { "context": 131072, "output": 4096 }
        }
      }
    }
  }
}
```

Replace `sk-...` with your AI Hosting API key. You create it in the **AI-Hosting**
section of your mStudio project — see
[Gaining access](/docs/v2/platform/aihosting/access-and-usage/access). An mStudio API
token from your profile settings is a different credential and will not work here.

:::note[Declare `tool_call` explicitly]
Without `"tool_call": true`, opencode will not offer the model its tools, and the agent
can only produce text — it cannot edit files or run commands. Set it on every model you
intend to drive the agent with. `GLM-OCR` above is the counter-example: it has no
tool-calling support at all, so it is declared with `"tool_call": false` and kept out of
the agent's model rotation. Check each model's limits on its page in the
[AI models documentation](/docs/v2/platform/aihosting/models).
:::

:::note[opencode 2.x reads this configuration unchanged]
The example uses the 1.x configuration format, which opencode 2.x still supports. It reads the
same files and converts the `provider` block when it loads them. 2.x ignores the per-model
`reasoning` field and logs a warning about it; that doesn't affect thinking, which the model
controls on the server side. 2.x also has a native format (`providers`, `package`, `settings`,
`capabilities.tools`), described in opencode's
[migration guide](https://opencode.ai/v2/docs/migrate-v1/). Converting to it is optional. Don't
convert a file that opencode 1.x still reads, because 1.x doesn't understand the native 2.x
format.
:::

## Verifying the connection {#verify}

```bash
opencode run --auto "Create a file called hello.txt containing the word hello, then read it back."
```

Expected: opencode writes the file, reads it back, and reports the contents. Run this in
a scratch directory — the agent writes files where you start it. A plain question would
succeed even with `tool_call` missing, which is why the check writes a file.

Without `--auto`, you need to approve the file write before it happens. `--auto`
auto-approves permissions that are not explicitly denied. In opencode 2.x, `--standalone`
runs against a private server instead of the shared background service — useful if
`opencode run` produces no output (see [troubleshooting](#no-output) below). opencode 1.x has
no background service and no `--standalone` flag.

## Usage {#usage}

```bash
# Explain unfamiliar code
opencode run "explain how session handling works in this project"

# Make a change
opencode run "add email validation to the registration form"

# Optimise
opencode run "optimize the database queries in user_service.py"
```

## MCP servers {#mcp}

MCP servers are declared in the top-level `mcp` object. Each entry is one of two
shapes:

- `"type": "local"` — `command` is an **array**: the executable followed by its
  arguments. `environment` is optional and sets environment variables for the server.
- `"type": "remote"` — `url` points at an MCP endpoint.

```json
{
  "mcp": {
    "context7": {
      "type": "remote",
      "url": "https://mcp.context7.com/mcp",
      "enabled": true
    },
    "fetch": {
      "type": "local",
      "command": ["uvx", "mcp-server-fetch"],
      "enabled": true
    },
    "playwright": {
      "type": "local",
      "command": ["npx", "-y", "@playwright/mcp"],
      "enabled": true
    },
    "sequential-thinking": {
      "type": "local",
      "command": [
        "npx",
        "-y",
        "@modelcontextprotocol/server-sequential-thinking"
      ],
      "enabled": true
    },
    "directus": {
      "type": "local",
      "command": ["npx", "-y", "@directus/content-mcp"],
      "environment": {
        "DIRECTUS_URL": "https://your-directus-instance.com",
        "DIRECTUS_TOKEN": "your-directus-token"
      },
      "enabled": true
    },
    "opensearch": {
      "type": "local",
      "command": ["uvx", "opensearch-mcp-server-py"],
      "environment": {
        "OPENSEARCH_URL": "https://localhost:9200",
        "OPENSEARCH_USERNAME": "your-opensearch-username",
        "OPENSEARCH_PASSWORD": "your-opensearch-password"
      },
      "enabled": true
    },
    "typo3": {
      "type": "local",
      "command": [
        "mw",
        "app",
        "exec",
        "--quiet",
        "--installation-id=a-XXXXX",
        "vendor/bin/typo3",
        "mcp:server"
      ],
      "enabled": true
    },
    "mittwald": {
      "type": "remote",
      "url": "https://mcp.mittwald.de/mcp",
      "enabled": true
    }
  }
}
```

For the mittwald server's authentication and token lifecycle, see
[MCP Integration](/docs/v2/agentic-integration/mcp/). The TYPO3, Directus and
OpenSearch servers authenticate through the environment variables shown above.

## Plugins and skills {#plugins-skills}

Plugins are listed in the `plugin` array:

```json
{
  "plugin": ["opencode-scheduler"]
}
```

:::warning[1.x plugins don't run in opencode 2.x]
opencode 2.x has a new plugin API and calls the array `plugins`. Plugins written for 1.x don't
load in 2.x, even if you rename the key. `opencode-scheduler` is one of them: it's built
against the 1.x plugin API. Before you upgrade, check whether each plugin you use supports 2.x.
:::

Skills go in `~/.config/opencode/skills/`, one directory per skill.

Agent packs add preconfigured subagents, each of which can point at its own model.
Routing subagents to `Qwen3.6-35B-A3B-FP8` while the main agent stays on
`Qwen3.8-27B-NVFP4` with thinking on (the model's default) keeps long sessions responsive,
since subagent work is mostly search and summarising.

## Troubleshooting {#troubleshooting}

### `opencode run` produces no output and writes no file {#no-output}

`opencode run` is non-interactive, and depending on the build it may return nothing —
no output, no file, no error — rather than reporting what went wrong. In opencode 2.x,
`--standalone` runs the command against a private server instead of the shared background service,
which is worth trying if a run produces nothing; this is the documented purpose of the
flag, not a guarantee it resolves the issue for every installation. If `opencode run`
still doesn't confirm the connection, fall back to the interactive TUI (run `opencode`
with no subcommand) and send the same prompt there.

### The agent answers but never edits a file or runs a command {#no-tool-calls}

The model is missing `"tool_call": true` in its `models` entry.

### The agent keeps repeating the same tool call {#repeated-tool-calls}

The agent reads the same files again and again and never gets to an edit. By default opencode
doesn't stop such a loop, and every iteration counts against your token quota. Set a step limit
for each agent in `opencode.json`:

```json
{
  "agent": {
    "build": { "steps": 30 },
    "plan": { "steps": 30 }
  }
}
```

`steps` is the maximum number of agentic iterations. When the agent reaches it, opencode asks the
model to summarise its work instead of making another tool call.

The limit ends a loop but doesn't prevent it. Loops happen mostly with thinking off. With
`Qwen3.8-27B-NVFP4`, switch thinking on for planning and tool work, see
[Agent loops in non-thinking mode](/docs/v2/platform/aihosting/models/qwen3-8-27b-nvfp4#non-thinking-agent-loops).

### An MCP server never starts {#mcp-server-fails}

Check the entry shape. A `local` server needs `command` as an array, not a string with
a separate `args` field — a string `command` with `args` is Claude Desktop's format,
and opencode ignores it silently rather than erroring.

If the server starts but fails to authenticate, check the name of the variables key. opencode
expects `environment`. It drops an `env` key without a warning, so the server starts without
its credentials.

### `npx` reports a 404 for an MCP package {#package-404}

Verify the package name. The context7 server is published as
`@upstash/context7-mcp` — the similarly named `@context7/mcp-server` does not exist
on npm.
